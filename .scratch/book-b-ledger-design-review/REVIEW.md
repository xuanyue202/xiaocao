# Book B 动态资本与账本独立审查

Status: analysis-complete; proposed accounting/storage design, not deployed
Date: 2026-09-29
Reviewed source HEAD: 0e21cacbcc0bd22117189ef58586a00e3e849df7

## 结论

建议建立 SQLite 的统一记账模块，使用追加的、可追溯的复式分录，生成可查询的累计资金明细、持仓成本、每日资产净值与收益报表。JSON/JSONL 保留原始回执、不可变证据和导出用途。这是设计建议；本轮没有迁移账本、改动执行策略、追加资金划拨或操作 APP。

需要先修经济事实的分类，再换存储。当前并非只有一份 JSON 余额：已存在委托意图、执行事件、自有成交证据、资金划拨和结算文件，有锁、幂等性及 hash 校验。它们有审计价值，但不是完整且事务统一的金融总账。

## 本金的定义与动态资金

1. **期初资本基准**：指定起算时点的资本。当前实现的 30,000 是历史策略起算基准，不是已经核实的整个 APP 账户历史银行入金。应以独立的期初分录保存其时点、性质、来源和证据；不能每天用余额反推本金。
2. **累计净划拨**：后续真正转入策略的资本减转出资本，不含成交回款、分红、费用或估值变化。可用现金政策不要求把所有现金差异认作资本。
3. **累计净投入 = 期初资本基准 + 累计净划拨**。盈利留在账户继续投资不会增加净投入；追加资本才增加。
4. 在完整、口径一致的资产和资金历史下，**累计盈亏 = 当前资产净值 - 累计净投入**。缺历史证据只能报告从可证明起点以来的收益，不能补造账户全生命周期的本金或收益。
5. 可用现金只是买入预算的当前硬上限。冻结现金仍是资产；买卖只是现金和持仓之间转换。人工持仓不因采用全部可用现金政策就归属 Book B。paper 保持独立。
6. 收益率用资金划拨时点的单位净值增减份额；赚的钱再投入不增份额。回撤高点、暂停锁存与原历史保持连续。只有起算历史和划拨时点估值可靠时，才可声称完整收益率；未知历史必须显式保留缺口。

例：期初 30,000，盈利 3,000 后资产 33,000，追加 20,000 后资产 53,000。净投入 50,000、盈亏仍 3,000；单位收益仍为追加前的 10%，不能把收益率重算为 53,000 / 50,000 - 1 来代表同一段策略表现。

## 查到的具体缺口

### 高优先级：现金差额被直接单位化为划拨

`src/xiaocao/live/book_b_capital.py:207-230` 计算 `delta = available - cash`，非零时写入 `kind=app_available_cash_allocation` 并调整单位因子。账户绑定、当前自有成交覆盖和不可变快照能证明余额，却不能证明差额的经济原因。

这与当前 Operating Contract §6 描述一致；因此是合同与模型共同需要完善的设计问题，不是某次读回失败。用户授权的是以可用资金动态调度，并未要求把真实账务损益从收益中移除。

反例：账面现金 10,000，APP 因额外实扣手续费降为 9,995，持仓不变。若将 -5 记为资本转出，会降低净投入、用单位化消掉这 5 元真实费用对表现的影响；分红也可能被当成新增资本而漏计收益。这个反例说明当前分类不足，不证明当前账户已经发生了该差错。

建议引入有来源的资本划拨、费用、分红/利息、成交和公司行动类型。未解释余额差记入待对账项，不自动修改净投入或绩效份额。该缺口不自动将已证明可用现金认作不可用，也不新增固定金额仓位上限；提交现金约束与收益会计质量分开处理。对账差额对资产/归属构成的实际风险仍走原有正式门。

### 中优先级：现金变动不是已实现盈亏

`src/xiaocao/live/book_b_live_lifecycle.py:971-979` 与 `buy_preflight.py:220` 的 `realized_cash_delta` 实际是现金减净划拨再减期初资本。买入未卖出的股票就会使它变负，故不能作为已实现盈亏字段。

`tests/test_book_b_available_capital.py:test_buy_over_legacy_seed_replays_with_owned_fees` 也明确期待买入后该字段为 -60,006，证明其真实语义是交易造成的现金净变动。已实现盈亏须使用卖出净收入减对应卖出份额的含费历史成本；浮动盈亏须使用剩余份额成本与当前估值。费用入成本或当期费用必须统一，禁止两次扣除。

### 中优先级：费用和净值口径需要明确

`book_b_live_lifecycle.py:852-893` 通过计划 fee_rate 重放现金；`934-956` 使用预计卖费计算清算价值。目前不是逐笔实扣费用总账，不能把估算费用称为已证明的实际费用。

正式账面 NAV 建议使用策略现金（含归属已证实的冻结现金）加自有持仓当前市值，扣已发生并应计的费用/负债；预计清算净值另列，供原有保守仓位与风险口径使用。此建议不在本轮改变现行退出费后策略 NAV 的仓位基数。报告应分别标注估算和实扣，不能将预计退出费当作已发生损失。

### 中优先级：多文件一致性与金额精度

`book_b_capital.py:233-243` 先落不可变快照，再追加资金链并 fsync；锁和严格读回能够防止多种重复/混写，却不是跨文件的数据库事务。中断可能产生孤立快照或不完整追加，需要现有失败关闭和恢复协议。

金额重放部分用 Decimal/十进制字符串，但状态输出和累计划拨重新经 float 传递（`book_b_capital.py:146-149`、`BookBLiveAccountState`），估值与费用口径也分散在多个重放位置。长期明细应统一已入账金额的精度与舍入规则，而非在展示层修补。

## 建议的账本内容

用户可见的累计明细至少包含：事件 ID、发生/确认时间、账户/Book/环境、事件类型、委托/成交 ID、证券与 lot、数量/单价、成交额、实际或估算手续费、现金变化、成本变化、净投入变化、已实现盈亏、证据引用、确认状态。不能只有每日余额快照。

内部按以下概念组织关系表（表名为方案，未实现）：

- `accounts`：Book、APP 仿真环境、账户绑定及起算信息。
- `source_events` / `evidence_refs`：原始事实 ID、来源哈希、时间、实际/估算/未证明状态。
- `journal_entries` / `journal_lines`：一笔业务多条平衡分录，正式入账后禁止改写，纠错用冲正与新分录。
- `lots` / `lot_allocations`：买入含费成本、卖出份额成本分配及剩余成本。
- `capital_flows` / `unit_events`：有来源的净投入和份额增减，保留原风险历史。
- `nav_marks` / `reconciliations`：时点估值、明细 head、差异及可证明的日结状态。

一期聚焦会计分录和报表，不必为换库重写整个委托系统。成交源唯一键需含环境、账户及权威成交身份；分批成交使用各自事实身份，不能只按委托 ID 去重。所有正式记账通过同一模块 interface 完成，早盘、盘中、EOD 和周报读取同一投影；读余额不应隐式追加资本事件。

已入账人民币使用整数分；单价、比例成本分摊与单位净值使用明确精度的 Decimal/定标整数或十进制字符串。残余分配和费率舍入有统一规则。SQLite REAL 不是精确金额类型。

## 存储选择

- JSON/JSONL：继续适合不可变原始证据、审计导出和可读回执；不必否定现有证据链。单文件格式并不阻止正确记账，但多文件事务、约束和查询需要持续自建。
- SQLite：建议承担正式会计分录与查询。使用本机持久盘、单写者、短事务；把同一事件的来源登记、分录、成本变动和投影更新置于同一事务，唯一约束防重复，约束检查账户/精度/分录平衡。数据库不自动保证正确的经济分类。
- SQLite 与 APP 提交仍不能构成同一事务。既有 durable claim、唯一 ACK、UNKNOWN reconcile-only 和账户资源锁必须保留。导出 JSON 不得成为第二个独立会计 writer。
- 保留 ADR 0007 单运行节点；不通过同步盘/网络文件系统让两台机器同时写 SQLite。备份应包括一致性校验及恢复验证，使用 SQLite 备份接口或已停写的完整交接，不能只拷一个仍在使用 WAL 的主文件。

SQLite 官方依据：

- https://www.sqlite.org/whentouse.html — 本地设备、低写并发的适用性；单 writer；多机网络直写限制。
- https://www.sqlite.org/transactional.html — 同一事务原子提交与崩溃恢复。
- https://www.sqlite.org/floatingpoint.html — 整数范围内精确，REAL 是近似值。
- https://www.sqlite.org/wal.html — 同机并发和 WAL/SHM 文件生命周期。

## 建议的迁移与验收

1. 先定型经济事件、实际/估算费用、NAV 和本金术语，修正差额分类与误导性字段；同步修订 §6 和消费者，而不是仅改文件后缀。
2. 使用现有不可变成交、划拨、快照建立只读 SQLite 投影和用户明细表。每条可追溯至原始证据，历史待证差异如实留存；已批准首次政策划拨单独标记迁移事实，不追认为银行入金。
3. 重放并逐项比较现金、每个 lot 的数量/成本、净投入、正式/清算 NAV、单位净值、原风险高点和暂停。历史 UNKNOWN 不转换为终态；旧凭证不重写。
4. 使用实际生产事实做只读影子对照。另行在允许工程时段验证部分成交、跨日、费用差异、分红、冻结/解冻、充值/转出、重复导入、崩溃恢复及并发幂等；本轮只阅读代码/测试，未运行 APP 工程测试。
5. 对照及恢复验证通过后切换唯一会计 writer。旧账冻结作为审计输入，JSON 导出成为 DB 投影；停止双写两套真相。迁移不触发委托重提、补成交或重置风险历史。

本轮没有声称某个实际现金差额的原因已知，也没有把当前 JSON 证据链损坏当作事实。结论是现有机制不足以长期充当完整、可解释的资金与收益总账。
