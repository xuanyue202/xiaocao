# KOL 投资情报 MVP

Status: ready-for-agent

## Problem Statement

用户关注的小草、吕晓彤、路西法等 KOL 会通过企业微信、小鹅通直播、百度网盘订阅、图片、文字和视频持续发布高密度投资信息。用户工作繁忙时无法及时观看直播或逐项处理订阅内容，因而会错过宏观拐点、市场风险、选股观点以及明确的买卖信号。现有信息获取方式高度依赖人工：打开微信消息、进入可能带密码的直播、抓取并压缩视频、上传或转存百度网盘、启动文稿和 AI 笔记生成、等待异步任务、导出文稿，再结合当下市场自行判断。信息一旦晚处理，价值就会下降，但一条趋势判断也不能因为隔了一天就被机械判定过期。

用户需要的不是简单搬运 KOL 原话，而是一条低人工成本、可恢复、可追溯的投资情报闭环：保留原始证据，提取全资产范围的观点，结合处理时的市场事实重新判断，及时向家庭组合提供建议，并把符合条件的美股动作送入一个大胆但无真实资金风险的独立模拟交易簿。MVP 可以接受用户每天约五分钟的配合，但必须为后续全自动化和捕获节点、分析节点拆机留下清晰边界。

## Solution

系统以可恢复的任务账本连接五个阶段：来源捕获、内容富化、观点标准化、当下市场综合判断、输出路由。开发期允许在当前 Mac 共置验证，但目标运行边界从第一版就固定为两个角色：7×24 小时协调节点持续负责所有低流量监听与执行；宽带媒体节点只负责必须由用户在场触发、或会在本机搬运大视频的任务。

第一条验收链路以小草直播为主：系统先启动并检查现有直播抓取服务，建立只接受新内容的捕获任务；用户在企业微信中打开“小草-专栏”的目标卡片、必要时输入直播密码并播放；系统通过本地服务发现直播，按已验证的保存路径直接生成压缩视频且不保留原始大视频。视频随后进入可替换的富化阶段，产生文稿和可读的 AI 笔记。系统读取文稿与笔记，提取 KOL 原始观点、推理链、标的、方向、时间尺度和证伪条件，再结合当下市场数据形成系统判断。

第二类输入以吕晓彤的持续订阅为代表。由于更新不定时且百度网盘目录/订阅状态轮询只消耗少量元数据流量，7×24 小时协调节点必须主动发现新内容，而不是要求用户定期检查。文字直接进入标准化入口，图片先 OCR；视频优先在百度网盘内完成云端转存、文稿和 AI 笔记生成，再进入同一个入口。只有当某一步不可避免地需要本地下载/上传大视频时，才把该媒体任务交给宽带节点。百度网盘是可替换的富化器和低流量发现边界，不是所有来源必须经过的公共总线。

每条高密度内容都产生两类相互隔离的输出：一是面向用户家庭组合的咨询性通知，覆盖 KOL 涉及的股票、港股、期货、宏观和其他资产，明确买入、加仓、持有、减仓、卖出或等待建议；二是面向独立 `Book KOL-US` 的美股模拟交易动作。家庭组合只给建议，不执行真实交易；模拟簿只交易美股上市股票和 ETF，不使用保证金、期权、期货、做空或负现金，但允许把杠杆/反向 ETF 当作现金买入的证券。模拟交易应在高质量机会出现时果断行动，不以僵硬的固定仓位数字压制机会，同时必须记录判断依据、集中度风险和证伪条件。

MVP 允许在确有必要时人工触发、输入密码或搬运大视频，但每一步都必须有明确状态、幂等恢复点和失败重试路径。小草直播在当前阶段由用户在宽带节点触发并完成本地抓取、压缩和必要的大视频上传；一旦产生云端视频或轻量工件引用，7×24 小时节点接管后续状态推进。百度网盘轮询、云内转存、AI 任务发起与检查、小文稿下载、OCR/分析、通知和模拟交易默认全部运行在 7×24 小时节点。

## User Stories

1. As a 忙碌的投资者, I want 系统及时处理我关注的 KOL 内容, so that 我不会因为工作繁忙错过重要市场信号。
2. As a 家庭组合成员, I want 系统把我们视为一个整体组合, so that 建议能够反映家庭共同持仓与风险而不是割裂的个人账户。
3. As a 用户, I want 每条具有当前决策价值的内容都收到通知, so that 没有发生模拟交易时我仍能获得重要宏观、风险和买卖信息，而纯低密度片段不会制造噪声。
4. As a 用户, I want 通知区分 KOL 原话与系统综合判断, so that 我能判断信息来源并避免把二次推断误认为原始建议。
5. As a 用户, I want 通知包含买入、加仓、持有、减仓、卖出或等待的明确动作, so that 信息可以直接辅助我的个人交易决策。
6. As a 用户, I want 每个建议包含信心、时间尺度和证伪条件, so that 我知道何时继续相信以及什么情况下需要改变判断。
7. As a 用户, I want 系统保留 KOL 的推理链和事实依据, so that 我可以持续校验这个人的判断质量。
8. As a 用户, I want 系统保存原始证据位置与处理时间, so that 之后能够回查观点是否被准确理解。
9. As a 用户, I want 系统结合处理时的最新市场事实重判旧观点, so that 延迟处理不会机械复制已经变化的交易动作。
10. As a 用户, I want 趋势观点通过证伪条件而不是固定一天有效期管理, so that 有效判断不会因为跨日被错误丢弃。
11. As a 用户, I want 系统明确展示多个 KOL 的一致与冲突, so that 我能够兼听则明而不是盲从单一来源。
12. As a 用户, I want 后续可以增加更多 KOL 并记录其历史可信度, so that 信息筛选能力会随事实验证逐步提高。
13. As a 小草订阅用户, I want 系统在我播放目标直播前先进入就绪状态, so that 我的操作不会因为抓取服务未启动而浪费。
14. As a 小草订阅用户, I want 系统只捕获建立任务后出现的新直播, so that 历史候选不会被误当作本次内容。
15. As a 小草订阅用户, I want 我可以负责点击企业微信卡片并输入直播密码, so that MVP 不必先攻克高风险且脆弱的微信全自动控制。
16. As a 用户, I want 系统直接保存压缩后的视频且不保留原始流, so that 存储与上传成本保持可控。
17. As a 用户, I want 下载失败后从现有任务恢复, so that 不需要重新播放或重新开始整条链路。
18. As a 用户, I want 批量视频在启动文稿和 AI 笔记后继续处理下一条, so that 远程生成的等待时间不会阻塞吞吐。
19. As a 用户, I want 文稿生成与 AI 笔记生成分别记录状态, so that 一个完成不会被错误当作两个都完成。
20. As a 用户, I want 系统至少等待五分钟后再按退避策略检查异步任务, so that 不会持续轮询并浪费 token 与资源。
21. As a 用户, I want 文稿导出失败时只执行明确的重试动作, so that 自动化不会随机点击相邻的复制或视频下载按钮。
22. As a 用户, I want 系统用同名云端文稿和最终本地文件作为持久完成证据, so that 短暂消失的“已导出”提示不会成为唯一成功判断。
23. As a 用户, I want 系统只下载文稿而不下载 AI 笔记, so that 正常流程保持最短且避免无价值文件搬运。
24. As a 用户, I want 系统在百度网盘内直接阅读 AI 笔记, so that 可以利用已有云端生成结果而不增加下载步骤。
25. As a 吕晓彤订阅用户, I want 文字更新直接被读取, so that 简单内容不必经过视频链路。
26. As a 吕晓彤订阅用户, I want 图片更新经过 OCR 后进入同一分析入口, so that 图片中的观点与交易信号不会丢失。
27. As a 吕晓彤订阅用户, I want 视频在转存和生成文稿后进入同一分析入口, so that 不同媒介产生一致的输出。
28. As a 系统运营者, I want 每个来源有独立适配器, so that 微信、小鹅通、百度订阅和未来社交平台不会耦合到核心判断逻辑。
29. As a 系统运营者, I want 已有文字、图片、网页和转录材料绕过百度网盘, so that 百度网盘不会成为不必要的公共依赖。
30. As a 系统运营者, I want 百度网盘富化器可以被本地 ASR 或其他云服务替换, so that 成本、流量或产品变化不会破坏整个系统。
31. As a 系统运营者, I want 优先使用本地 API、CLI 或浏览器 DOM 等确定性接口, so that 高频流程不依赖慢且脆弱的屏幕坐标识别。
32. As a 系统运营者, I want 默认方案完全不采用 Computer Use, so that 已被本轮实验判定为不可靠的自动化方式不会进入 MVP 主链路。
33. As a 系统运营者, I want 每个外部操作前后持久化检查点, so that Codex 或应用中断后可以继续而不是重做。
34. As a 系统运营者, I want 任务账本只追加事件, so that 状态变化、失败与重试都可以审计。
35. As a 系统运营者, I want 所有低流量且需要持续监听或执行的任务默认运行在 7×24 小时节点, so that 不定时更新无需依赖我记得检查。
36. As a 系统运营者, I want 大视频的本地抓取、下载和上传只运行在宽带节点, so that 7×24 小时节点不会消耗大量手机流量。
37. As a 吕晓彤订阅用户, I want 7×24 小时节点自动轮询百度网盘的新订阅内容, so that 不定时更新不会因为我忙或忘记而延迟。
38. As a 系统运营者, I want 百度网盘内的云端转存和 AI 处理由 7×24 小时节点协调, so that 不涉及本地大视频传输的工作无需人工介入。
39. As a 用户, I want MVP 的日常人工成本控制在约五分钟内, so that 即使第一版不能全自动也仍然值得长期使用。
40. As a 模拟交易研究者, I want KOL 观点覆盖全部资产类别但模拟执行只选择美股, so that 情报不丢失且第一版交易范围足够聚焦。
41. As a 模拟交易研究者, I want `Book KOL-US` 与 Book B、Book T 以及真实家庭账户隔离, so that KOL 实验不会污染现有策略评价与资金状态。
42. As a 模拟交易研究者, I want 高质量机会出现时模拟簿可以大胆集中, so that 研究不会因为机械保守而注定平庸。
43. As a 模拟交易研究者, I want 任何仓位决定都解释机会质量与集中度风险, so that “果断”仍然能够被复盘和验证。
44. As a 模拟交易研究者, I want 模拟簿禁止保证金、期权、期货、直接做空与负现金, so that 激进实验仍处于清晰的风险边界内。
45. As a 模拟交易研究者, I want 在理由充分时可以买入杠杆或反向 ETF, so that 不使用账户杠杆仍能表达强烈方向判断。
46. As a 模拟交易研究者, I want 每条内容要么产生模拟动作要么记录明确不交易原因, so that 可以区分没有机会与系统漏处理。
47. As a 模拟交易研究者, I want 每笔模拟动作引用对应证据、当下验证与证伪条件, so that 后续可以评估 KOL、综合判断和执行各自贡献。
48. As a 真实资金账户所有者, I want 系统永远不替我执行家庭组合交易, so that 个人建议不会越过真实资金授权边界。
49. As a 家庭组合成员, I want 每个有效发布事件在灰常亮保留一份完整稳定报告, so that 企微只需承担及时入口而不会损失完整信息。
50. As a 用户, I want 完整直播只要包含当前有效的姿态、动作、仓位或触发条件就提醒, so that “继续持有”或“继续等待”不会因为观点未反转而被漏掉。
51. As a 用户, I want 零可归属投资主张的短图片或只言片语停在低密度审计终态, so that 无信息内容既不污染灰常亮也不打扰家庭。
52. As a 用户, I want 历史观点只在新发布、期限/条件到期、重大事实变化或我主动请求时定向复核, so that 当前观点既不会机械跨日失效也不会因无反例自动续期。
53. As a 系统运营者, I want 协调节点在北京时间 07:00–23:00 每小时短暂运行一次并在夜间静默, so that 不定时更新最多延迟约一小时且不会维持无意义的常驻轮询。

## Implementation Decisions

- 流水线采用五段式领域边界：来源捕获、内容富化、观点标准化、当下市场综合判断、输出路由。来源与富化适配器不能把平台细节泄漏到判断层。
- 最高层、首要验收 seam 是“一个有真实证据的 KOL 内容进入系统，最终产生可追溯的标准化情报、家庭组合建议，以及一个 `Book KOL-US` 动作或明确不交易理由”。每个来源 ticket 都沿用这一条端到端 seam，只逐步把输入边界从现成文稿向视频、直播和订阅扩展。
- 首个 tracer bullet 同时使用小草、吕晓彤和路西法各一份真实视频文稿，证明同一标准化、当下市场验证、家庭通知和 `Book KOL-US` 路由契约能够处理三位 KOL，而不是把小草的表达习惯写死在核心模型里。该验收同时覆盖观点一致、观点冲突、非美股观点只提醒、以及美股观点可模拟执行等场景。
- MVP 首个 P0 来源是小草企业微信卡片与小鹅通直播；吕晓彤持续订阅是第二类输入，先覆盖文字、图片 OCR 和已转存视频；路西法当前依赖闲鱼购买临时分享链接，获取成本和稳定性不足，不作为 P0 自动来源。
- 捕获阶段复用现有本地抓取服务，通过其 API 建立基线、发现新直播、启动下载和查询任务，不修改该服务的现有脏工作区。
- 捕获下载必须复现已验证的“保存”语义：任务类型为直播捕获、启用流式压缩、产物使用 `-compressed.mp4`，正常流程不保留原始视频。
- MVP 接受用户在系统就绪后完成微信点击、直播密码输入和播放。密码、百度 Cookie、微信凭据及其他秘密不写入任务账本或源码。
- 所有任务使用 append-only 事件账本，至少覆盖等待捕获、已捕获、下载中、下载完成/失败、上传中、已上传、文稿处理中、AI 笔记处理中、已富化、已分析、已通知。文稿与 AI 笔记是同一父任务下的独立子状态。
- 外部步骤必须幂等并可从最后成功检查点恢复。失败只重试对应子步骤，不重新创建整条任务；重复运行不能重复通知或重复下模拟订单。
- 百度网盘是可替换的异步富化器，不是公共消息总线。文字、图片 OCR 结果、网页和已有文稿直接进入标准化入口。
- 百度富化正常流程只要求下载文稿；AI 笔记在网盘内读取，不导出。文稿本地完成证据是精确同 basename 的文档文件；云端同名文档是导出成功的持久后备证据。
- 百度自动化默认只考虑稳定官方/本地 API 或 CLI，以及复用登录态的浏览器 DOM/OpenCLI。本轮实验已经证明 Computer Use 在该场景下自动化不可靠，因此不进入默认设计、实现计划或验收路径。只有前述确定性方案均被实际验证为不可行，且某个必要步骤不存在其他方案时，才允许把 Computer Use 作为最后例外单独提案，而不是自动降级使用。
- BaiduPCS-Go 一类文件 CLI 只适合列目录、精确定位和下载文稿，不能被假定为能够触发百度 AI 生成。是否采用及其登录维护成本由开发 session 做一个受限 spike 后决定。
- 富化 worker 启动文稿与 AI 笔记后立即处理下一视频；单任务至少五分钟后才第一次轮询，并使用退避。批处理不能因一个视频的 5–20 分钟等待而串行阻塞。
- 标准化情报必须保存来源、作者、标题、发布时间、捕获时间、处理时间、证据引用、资产类别、标的、方向、动作、时间尺度、置信度、推理、证伪条件，以及 KOL 声明与系统综合判断的明确边界。
- 观点没有固定跨日失效规则。系统在处理时用当下市场数据重新验证；时效由论点的时间尺度、事实变化和证伪条件决定。
- 多 KOL 输出保留共识和冲突，不以简单投票替代判断。KOL 历史可信度是后续可积累的证据维度，不在 MVP 中自动决定交易权重。
- 家庭组合是唯一的个人建议对象。通知覆盖全资产观点，但只提供咨询性动作，不调用任何真实资金执行接口。
- 来源条目先通过投资内容价值门。零可归属投资决策主张者停在持久低密度审计终态，不生成灰常亮报告或企微提醒；一旦升级为真实发布事件，必须生成一份完整稳定的灰常亮报告，并独立形成企微已送达/合法不提醒与 Book KOL-US 动作/不交易三项终态。
- 完整直播采用宽松提醒口径：存在当前市场姿态、买卖或持有动作、仓位边界、方向选择、可执行触发条件任一项即可提醒，不要求观点相对上一场发生反转。历史初始化、修订、已过时盘中信息、纯确认或纯方法教学可以只发布灰常亮报告并记录不提醒原因。
- 企微提醒必须在灰常亮发布回执之后发送，先给最重要洞察，再连贯概括其余重要信息，最后附唯一稳定报告链接。不同事件不合并成批次摘要；夜间积压在次日 07:00 按决策重要性逐事件处理。
- KOL 长期观点只在同一 KOL 新发布、期限/触发/证伪条件到期、相关重大事实变化或用户请求时定向复核。纯观点评估只追加到灰常亮当前/历史投影，不制造合成发布事件、企微提醒或 Book 动作。
- `Book KOL-US` 是新的独立 paper-only 生命周期，不复用或污染现有短线 Book B 与趋势 Book T 的账户、持仓、交易记录和评价口径。
- `Book KOL-US` 只允许美股上市股票及 ETF。禁止保证金、期权、期货、直接做空和负现金；杠杆/反向 ETF 作为现金证券允许买入。
- 模拟仓位由机会质量、证据一致性、市场验证、流动性与组合集中度共同决定，不设置为了保守而保守的固定小仓位。任何集中动作必须解释风险及退出/证伪条件。
- 节点归属按资源特征而不是按 KOL 划分。7×24 小时协调节点拥有定时/不定时轮询、元数据去重、云内转存、AI 任务发起与轮询、小型文稿/图片获取、OCR、市场验证、通知和 Book KOL-US；宽带媒体节点拥有用户在场的小草触发、本地直播抓取/压缩及任何不可避免的大视频本地下载/上传。开发期可以共置，但实现必须通过轻量任务和工件引用保持这条边界。
- 吕晓彤的百度网盘订阅属于 7×24 小时协调节点的自动发现范围。首次登录、授权或页面语义确认可以要求用户配合；日常不允许把“检查有没有更新”作为用户任务。若视频能够在百度网盘内转存和富化，7×24 小时节点直接推进；只有明确需要本地搬运大文件时才创建宽带节点 handoff。
- 吕晓彤只实现一条日常发现路径：7×24 节点直接低流量轮询本机私密配置中的“彤商学院防断更新”分享 URL，读取文件清单及最新修改时间，发现新增或变更文件后按媒体类型处理。真实分享轮询测通后即结束来源探索，不再实现 `订阅分享管理` 消息解析、并行适配器或预防性 fallback。URL 或分享码变化时由用户更新本机 `xiaocao.yaml`；旧链接失效则明确提醒，不能暗中切换其他路径。URL、分享码和其他凭据只存在于被 Git 忽略的本机配置，不得写入 PRD、源码或任务账本。
- 路西法不要求建立自动购买或外部稳定订阅。用户继续负责合法购买内容并同步到私有目录 `/课程/路西法全套`；7×24 小时协调节点只轮询该目录的轻量元数据，以修改时间发现候选，并以路径、文件身份、大小/哈希等稳定证据完成去重。页面窄时分享浮层可能遮住目录名，因此实现不得依赖可视目录文字或坐标点击，应使用精确 hash-route、目录 API 或语义 DOM 直接绑定该路径。
- 日常调度只有一个 Codex Automation：北京时间 07:00–23:00 每小时唤起一次短任务，夜间不轮询，07:00 接续积压。正常无更新和可自动恢复的暂时失败静默；只有真正需要用户操作的阻塞才发送一次明确操作提醒，同一阻塞在状态变化前不重复提醒。
- MVP 的成功标准包含人工成本：正常单条直播只要求用户在收到就绪提示后完成约五分钟以内的打开、输密码、播放或必要拖拽操作；后续异步步骤由系统恢复推进。
- 已完成的可行性证据包括：本地抓取服务能够基线化发现新直播，能够使用正确的流式压缩参数产生压缩任务，任务状态可以持久化；百度网盘能够生成文稿与 AI 笔记，文稿可以导出为同名云端文档并下载。本轮同时形成一条明确负面结论：百度桌面 Computer Use 自动化不可靠，不能作为 MVP 默认方案。

## Testing Decisions

- 首要验收只测试外部可见行为，不断言内部函数调用或屏幕坐标。最高层端到端测试先以三位 KOL 的真实文稿为输入，后续来源 ticket 分别以真实视频、新小草直播和真实订阅内容为输入；所有切片都以标准化情报、家庭建议、模拟动作/不交易理由和完整证据链为统一输出。
- 端到端测试必须验证任务可以在任意异步检查点中断后恢复，且恢复不会重复下载、重复通知或重复模拟成交。
- 捕获适配器使用契约测试验证：旧候选不会被误报，新候选可被发现，下载请求启用正确的直播捕获与压缩语义，失败可强制重试，完成任务记录压缩媒体路径。现有捕获适配器测试是该层 prior art。
- 任务账本测试只验证可观察状态机：事件只追加、非法状态 fail closed、文稿与 AI 笔记可独立成功或失败、最新状态可从历史事件重建。
- 富化适配器使用录制响应或受控假服务验证异步提交、首次轮询延迟、退避、单子任务重试及批量非阻塞；不以等待真实 20 分钟作为日常单元测试。
- 百度 live acceptance 使用一个明确 basename 的压缩视频，验证生成文稿、生成 AI 笔记、导出同名云端文档和获得同名本地文稿。若采用浏览器 DOM/CLI，验收必须通过语义定位，不允许依赖固定坐标。
- 标准化层使用文字、OCR 文本、文稿和含错别字的 ASR 样例进行同构输出测试，验证 KOL 声明、系统推断、资产、动作、时间尺度与证伪条件不会混淆。
- 当下市场综合判断测试使用冻结市场快照，验证同一 KOL 观点在事实未变、事实支持、事实冲突和证伪条件已触发时产生可解释的不同结论；测试不能用“超过一天”作为唯一失效条件。
- 输出路由测试覆盖三层价值分流：零投资主张停在低密度审计终态；有信息但无当前提醒价值者只发布灰常亮；有当前决策价值者先发布灰常亮再发送一条企微提醒。通知失败可恢复且不重复报告、提醒或模拟成交。
- 家庭建议测试验证不会调用真实交易接口，并覆盖买入、加仓、持有、减仓、卖出、等待及全资产非美股观点。
- `Book KOL-US` 测试验证账户与 Book B/Book T 隔离、只接受美股股票/ETF、现金不可为负、禁止期权/期货/保证金/直接做空、允许合规的杠杆或反向 ETF。
- 模拟交易测试验证同一任务与同一动作具有幂等键；高置信机会可以形成明显仓位，但每个动作都有证据、集中度说明和证伪/退出条件。
- 节点边界使用协议级和真实闭环共同验证：宽带节点只发布轻量状态与本地/云端工件引用，7×24 小时节点无需下载源视频即可轮询订阅、推进云端任务、读取文稿并完成分析、通知和模拟交易。
- 日常运行验收验证唯一 Automation 的 07:00–23:00 小时级节奏、夜间静默、07:00 逐事件接续、无更新静默、用户阻塞只提醒一次，以及同一 KOL 的触发式观点复核不会产生企微或 Book 副作用。
- Live acceptance 与自动测试结果都必须写入可审计产物。只看到按钮点击、短暂 toast、传输角标或等待时间不构成完成证据。

## Out of Scope

- 本 PRD 不包含具体开发实现；开发、依赖选择和部署在新的 session 中进行。
- MVP 不追求企业微信、小鹅通密码输入和所有上传动作完全无人值守。
- MVP 不自动购买闲鱼分享链接，也不把路西法的临时购买流程做成 P0 来源；找到稳定持续订阅后再接入。
- MVP 不同时接入 X、小红书、抖音及大规模 KOL 池，只保留标准化入口和来源适配器扩展能力。
- MVP 不训练自有 ASR 模型，也不承诺立即替换百度网盘；只有成本、流量或可靠性证明需要时才切换。
- MVP 不把百度网盘作为所有来源的必经步骤，也不在正常流程下载 AI 笔记或原始大视频。
- MVP 默认不使用百度桌面 Computer Use。只有 API、CLI、浏览器 DOM/OpenCLI 等确定性方案全部经过验证仍不可行，且缺失步骤属于完成闭环的必要条件时，才允许另行评审是否采用该例外。
- MVP 不为 KOL 观点设置统一的固定有效期，也不把观点未经验证地写入确定性策略参数。
- MVP 不让 KOL 内容直接改变 Book B、Book T 或其他已验证策略的确定性脊柱；策略变化仍需遵守 Research Consumption Gate 和 Strategy Evolution Protocol。
- MVP 不执行家庭组合或任何真实资金交易。
- MVP 不在 `Book KOL-US` 中使用账户杠杆、期权、期货、直接做空或负现金。
- MVP 不在第一版建立复杂的 KOL 排名、收益分成或机器学习权重；先积累可追溯预测与结果。
- 开发期不要求立即完成两台物理机器的部署，但不得把需要持续运行的低流量任务设计成依赖用户或宽带节点在线；最终日常运行必须遵守既定节点归属。

## Further Notes

- 本轮调研的目的已经达到：核心链路在能力上可行，同时 Computer Use 在百度桌面场景中的速度、语义识别和操作稳定性均未达到自动化要求，应视为已证伪的默认方案。三位真实文稿切片完成用户验收后，下一 frontier 优先固定确定性的百度视频富化闭环，而不是继续扩大来源范围。
- 推荐的默认方向是浏览器登录态与 DOM/OpenCLI 负责百度 AI 页面动作，文件 CLI 负责同名文稿的发现与下载。该组合仍需在开发 session 用真实账号做最小验证后再定版；验证失败时应继续寻找确定性接口，而不是直接回退到 Computer Use。
- 百度导出的“已导出”提示会在数秒后消失。实现不得仅因自动化未截获 toast 就重复点击；刷新后出现精确同名云端文稿，以及最终出现精确同名本地文稿，才是更稳定的持久证据。
- 当前已验证的小草人工协作顺序是：系统先报告抓取服务就绪并 arm，用户再打开企业微信卡片、必要时输入密码并播放。顺序不能颠倒。
- 产品价值不以“抓了多少内容”衡量，而以重要信息是否及时进入个人决策、模拟簿是否形成可复盘动作、用户日常成本是否足够低衡量。
