# 2026-09-15 KOL 准备超时修复与 09:00 启动复盘

## 问题与根因

本次没有可执行 ★E 是正常策略结果，不属于故障。需要修复的是：09:25:33 的 KOL 审阅在 120 秒内未拿到有效决策，09:27:33 回退基线。

问题有三层：

1. **交接时点由任务收尾决定。** 昨日 writer 13:29 确实完成过准备包；今日 09:14 首篇文章完成发布及 ACK 后，继续处理第二篇和视频，尚未交付新准备包。任务仍在运行，不能用最终遗漏解释，但已错过晨间消费窗口。原流程缺少逐对象交接检查点。
2. **缓存可用性与语义变化混在一起。** 内容指纹由当前已加载记录计算；缓存过期会让历史观点消失、报告哈希变成空值，即使来源本身未变，也返回需要重新分析。
3. **准备检查只看现在，没有看消费时刻。** 昨日开盘集中读取的历史清单，在今日开盘附近跨过 24 小时期限。09:07 的 159/159 完整不能保证09:26仍完整；43个精确ID补读后又有30个过期。提前启动本身不能消除这个时间关系。

## 最终修复

- `DailyPublicationPipeline` 在单对象报告、提醒和 Book 终态后进入来源交接，完成精确报告/manifest/准备包绑定回执后才返回给上层；观点维护使用同一入口。准备失败不重放已发生的报告、提醒或 Book 效果。
- `trading_source_handoff.py` 保存不可变请求和完成回执，保留开始/完成时间。`kol_daily.py prepare-trading-sources --publication-key ...` 只恢复交接；下一次已获 writer 所有权的 sweep 先处理持久化未完成交接。已完成回执不再读远端或请求分析；内容未变时可直接复用原审核包和原上下文。
- 准备状态区分 `source_revalidation_required` 与 `source_analysis_required`。前者提供可复用笔记路径，但仍要求补验缺失清单；已知内容变更、记录删除或新增不会伪装成已准备。
- `--history-fresh-through` 按真实消费时点检查历史有效期，正常24小时TTL和真实证据as-of不变；长批次结束时再次核对，过期项必须返回精确缺口。
- 09:00 行情检查改为 `--scope authentication` 单次认证读取。空池不当作认证故障，990502与传输/结构错误仍显式阻断；需要具体端点诊断时才用完整 core 检查。
- 已更新现有晨间和 remote writer Automation，并通过工具重新打开。时刻、模型、通知偏好均保持原配置；不是只改仓库镜像。

## 09:00 是否必要，有什么副作用

09:00不是交易策略的必要时点，现阶段保留它是为了给认证恢复和来源补验留出余量。今日普通早期准备约09:07完成，之后约15分钟主要可以等待。是否进一步缩短到更晚，需要修复后的真实晨间耗时支持；当前没有足够证据保证固定五分钟能覆盖全部异常。

提前启动不是零成本：

- 常驻原 runner 和每秒本地冻结检查；Agent应分段sleep，不持续重复分析。
- 原有每30秒的native保活使用表面探针，必要时调用既有解锁，因此可能涉及界面/会话变化；它不提交订单。约25分钟最多是约50次保活周期，实际次数还取决于调用耗时。
- KOL清单补验有网络、缓存锁、token和磁盘成本；采用精确ID、未变化分析复用，禁止并行重复全库刷新。
- 09:00账户/行情不作为09:25或提交时刻的新鲜证据。资金分配与执行前市场门继续读取当前值。

因此保留09:00轻量就绪检查，完成后等待；09:22读取来源变化，冻结后只做当前适配。这里不延长120秒审阅、不降低覆盖门、不改变策略或订单规则。
