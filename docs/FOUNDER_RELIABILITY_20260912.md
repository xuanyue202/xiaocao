## APP 端到端补测与并发评估

### 已补的竞争测试

本节是初次 578 项验证之后的补充。新增 2、5、20 个同时到达的请求，分别检查同一计划重复调用、不同标的、同标的不同价格。使用独立 Python execution/store/adapter 对象、真实账户文件锁和同一个模拟 native 服务：同计划只提交/撤销一次；不同计划各有唯一订单号，代码、价格、数量不串单，倒序撤单仍精确匹配，原有无关订单不变。

另用两个真实 OS 子进程争用同一账户锁，确认后者等待、持锁进程被终止后后者可接续；测试只终止自己创建的测试子进程。它验证锁释放，不代表“进程在提交后退出”已完成 APP 对账——后者仍依赖持久 claim 和服务回执。

新增竞争用例 10 项，专项累计 **588 项**。线程测试的运行时间不是 APP 吞吐量；这些测试不打开 APP，也不增加仿真委托。首次进程故障注入的夹具在清理时触碰了已终止进程的 Event，导致夹具自身阻塞；清理改为只回收子进程，完成重跑，不改变业务锁实现。

### 优先补齐的 APP 场景

| 场景 | 为什么有必要 | 当前证据与下一步验收 |
| --- | --- | --- |
| 连续 2、5 笔提交，混合不同标的/同标的不同价格 | 单笔成功无法发现上一笔字段残留、弹窗残留、串订单号 | Python 批量映射已测；APP 应让数笔同时存在，再逐笔精确撤单并恢复资金，而非每提交一笔马上撤掉 |
| monitor 查询与早盘预填/提交/撤单竞争 | 查询会切 APP 页面，业务只读不等于 UI 无副作用 | 提交/撤单有账户锁；部分查询/预填路径没有共享同一完整操作边界，是优先隔离和故障注入的缺口 |
| 多进程、不同状态目录或 checkout | 锁文件目录不同会变成不同锁，即使操作同一 APP | 当前测试证明同锁目录有效；还需验证宿主机上同一 APP 会话的统一串行入口 |
| 中间第 k 笔超时、锁屏、断连或进程退出 | 前面可能已提交，后面尚未提交，不能整批重跑 | 单笔丢响应/重建已有覆盖；批次需要逐笔 claim、状态和原顺序恢复，UNKNOWN 先精确对账 |
| 接受、部分成交、撤单与新增成交交错 | 撤单期间可能又有成交，资金冻结与归属必须一致 | Python 部分成交终态已测；APP 撮合时段仍需观察成交/撤单交错，不能由周末撤单推断 |
| 委托超过一屏、列表重排、同代码多笔、历史日期切换 | 不能把可见行当成全部订单，不能按行号撤单 | 需要 APP 多行/滚动端到端证据，确认完整性和按订单号匹配；先少量再扩大 |
| 市场拒单与恢复 | 涨跌停价格、资金冻结、不可卖数量等会改变下一步 | 故障注入覆盖错误状态；APP 需要验证拒单弹窗被正确消费，下一笔表单仍可使用 |
| 性能 | 总耗时可能主要花在重复切页/OCR/初始化，而非输入 | 分别记录等待锁、准备、提交受理、对账、撤单耗时，比较单笔与批量总耗时；积累足够样本后才报告 P50/P95 |

优化原则：行情、KOL 和候选计算可在各自数据约束内并行；同一 APP 的表单和查询导航需要有序执行。先补齐所有 APP 调用共用的操作边界，再测批量请求排队。不能直接把逐单执行改成多个线程同时填单。优先消除已测出的重复查询、切页和无效等待；共享准备数据仍须保持新鲜度，保留逐单身份、资金约束与持久 claim。3 秒是普通动作响应的观察目标，不是取消必要读取的理由。

本次只增加离线竞争测试和端到端缺口评估，未改变生产并发模式，未新增 APP 订单。读写争用隔离、APP 多单性能和超过一屏委托仍为未完成验收项。
